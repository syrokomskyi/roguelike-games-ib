# RFC-0002: Concept quality — semantic equivalence mappings, noise filtering, and implementation reference integrity

## Context

PLAN-003 introduced two concept generation paths in `scripts/run-stage-concepts.ts`:

1. **Exact-match concepts** — groups records by `(kind, attribute, valueSlug)` across games; creates a concept when ≥2 games share the same attribute value. Currently produces 22 exact-match `cross_game_mechanic` concepts.

2. **Semantic equivalence concepts** — hand-curated mappings (`SEMANTIC_EQUIVALENCES` array) that normalize game-specific attribute values to canonical concept values via `VALUE_NORMALIZATIONS`. Currently produces concepts for Fire/Cold/Poison/Electricity/Acid/Sleep Resistance, Faction Membership, Creature Alignment, Flight Capability, and Item Material.

### Current problems

#### P1: Incomplete semantic equivalence coverage

The `SEMANTIC_EQUIVALENCES` mappings were initially written with Crawl `resists` and BrogueCE `conveys` attributes, but these were removed during manual editing because the values didn't match the normalization map. The current mappings only cover NetHack (`resistances`, `conveys`) and Cataclysm-BN (`flags`) for most resistance types. Crawl and BrogueCE are absent from most concepts despite having equivalent mechanics.

**Root cause**: Crawl stores resistances as boolean flags inside a `resists` object (e.g., `resists: { fire: true, cold: false }`), not as string values. BrogueCE stores them in a `flags` array with values like `RF_FIRE`. The current `extractAttributeValues()` function only handles arrays of strings, pipe-separated strings, and scalar strings — it does not handle object-valued attributes where keys represent the resistance type.

**Impact**: Fire Resistance concept has 3 games (broguece, nethack, cataclysm-bn) but is missing Crawl. Cold/Poison/Electricity Resistance are missing both Crawl and BrogueCE. This makes the cross-game comparison incomplete.

#### P2: Noisy exact-match concepts

The `NOISY_ATTRS` blocklist and minimum member threshold (8) were added to filter trivial concepts, but several noisy concepts still pass:

- `creature_speed_12`, `creature_speed_15`, `creature_speed_20`, `creature_speed_30`, `creature_speed_40`, `creature_speed_50` — these are numeric speed values that happen to coincide across games. They are not semantically meaningful cross-game mechanics; they are coincidental numeric matches.
- `creature_flags_flies` — this exact-match concept overlaps with the semantic equivalence concept "Flight Capability". Duplicate semantics under different concept names.

**Root cause**: The exact-match algorithm treats any attribute value match across games as a concept, regardless of whether the match is semantically meaningful. There is no notion of "informative attributes" vs "coincidental matches".

#### P3: Implementation reference integrity

Concepts store `implementation_refs` as arrays of record IDs and `ancestry.derived_from` as a subset of those IDs. These are not validated at concept creation time:

- If a source record is deleted or its ID changes (e.g., re-extraction with different hashing), the concept's refs become dangling.
- The Obsidian builder renders `implementation_refs` as wiki-links (`[[record-key]]`). If the target record doesn't exist in the vault, the link is broken.
- The `get_concept_members` MCP tool resolves `ancestry.derived_from` to records — dangling refs return `undefined` and are silently filtered.

**Impact**: Users see broken links in Obsidian and incomplete member lists in MCP responses. There is no diagnostic or test that catches this.

## Problem

Without addressing these three issues:

1. **Cross-game concepts are incomplete** — Crawl and BrogueCE are systematically excluded from resistance concepts due to attribute format mismatch. This undermines the primary value proposition of cross-game analysis.

2. **Concept namespace is polluted** — numeric coincidences and duplicate semantics dilute the signal. Users browsing the Concepts MOC see noise alongside meaningful concepts, reducing trust in the concept layer.

3. **Reference integrity is unverified** — there is no guarantee that concept refs resolve to actual records. This is a data quality issue that can silently degrade the knowledge base over time.

## Decision

### D1: Extend `extractAttributeValues()` to handle object-valued attributes

For semantic equivalence matching, attributes like Crawl's `resists` (an object with boolean values) need special handling:

```typescript
function extractAttributeValues(attrValue: unknown): string[] {
  // ... existing array/string handling ...

  // Handle object-valued attributes: extract keys where value is truthy
  if (typeof attrValue === "object" && !Array.isArray(attrValue)) {
    return Object.entries(attrValue)
      .filter(([_, v]) => v === true || v === 1 || v === "true")
      .map(([k]) => k);
  }

  return [];
}
```

This allows `resists: { fire: true, cold: false }` to produce `["fire"]`, which then normalizes via `VALUE_NORMALIZATIONS["Fire Resistance"]["fire"] = "fire"`.

**Files to modify**: `scripts/run-stage-concepts.ts` — `extractAttributeValues()` function.

**Implementation order**: Object-valued attribute handling (D1) must be implemented and tested before re-adding Crawl `resists` and BrogueCE `flags`/`conveys` to `SEMANTIC_EQUIVALENCES` mappings. Without the object handler, these mappings will produce no matches.

**Normalization map additions**: Add Crawl-specific and BrogueCE-specific value aliases:

```typescript
"Fire Resistance": {
  // ... existing entries ...
  "rf": "fire",       // Crawl internal abbreviation
  "res_fire": "fire", // Crawl alternative
},
```

BrogueCE flags like `RF_FIRE` need case-insensitive matching. The existing `normalizeValue()` already lowercases, so adding `"rf_fire": "fire"` to the map will match `RF_FIRE` after lowercasing.

### D2: Attribute informativeness classification

Introduce an `INFORMATIVE_ATTRS` allowlist for exact-match concept generation. Only attributes that represent meaningful game mechanics (not display metadata or coincidental numeric matches) should produce concepts.

**Classification criteria**:
- **Informative** (produce concepts): `material`, `alignment`, `holiness`, `default_faction`, `flags` (semantic), `resistances`, `size`, `shape`, `blood_type`, `abilities`, `species`, `categories`, `artifact_type`, `trap_value`, `skill_value`, `schools`, `parent_branch`
- **Non-informative** (already blocked by `NOISY_ATTRS`): `id`, `key`, `schema`, `glyph`, `color`, `symbol`, `sprite_path`, `tile_coords`, `sound`
- **Numeric-coincidental** (new filter): `speed`, `hp`, `hd`, `ac`, `ev`, `hp_10x`, `melee_dice`, `melee_dice_sides`, `dodge`, `volume`, `weight`, `price`, `difficulty`, `level`, `depth` — these produce coincidental matches that are not semantically meaningful

**Implementation**: Replace the `NOISY_ATTRS` blocklist with an `INFORMATIVE_ATTRS` allowlist. This is safer — new attributes will not produce concepts unless explicitly added.

```typescript
const INFORMATIVE_ATTRS = new Set([
  "material", "alignment", "holiness", "default_faction",
  "flags", "resistances", "conveys", "size", "shape",
  "blood_type", "abilities", "species", "categories",
  "artifact_type", "trap_value", "skill_value",
  "schools", "parent_branch",
]);
```

**Files to modify**: `scripts/run-stage-concepts.ts` — `generateExactMatchConcepts()` function.

**Note on `flags`**: The `flags` attribute remains in the allowlist because `creature_flags_stationary` is a legitimate cross-game mechanic (being stationary is semantically meaningful). Only `creature_flags_flies` is a duplicate of the "Flight Capability" semantic equivalence concept — D3 handles this deduplication. New `flags`-based concepts will continue to be generated; only those explicitly covered by a semantic equivalence mapping are deduplicated.

### D3: Deduplicate exact-match concepts against semantic equivalence concepts

After generating both exact-match and semantic-equivalence concepts, check for semantic overlap:

- If an exact-match concept's `(kind, attr, value)` triple is already covered by a semantic equivalence concept (e.g., `creature.flags.flies` is covered by "Flight Capability"), skip the exact-match concept.
- Implementation: after generating both sets, filter exact-match concepts whose `conceptSlug` matches a semantic equivalence concept's `conceptSlug` or whose attribute+value is a subset of a semantic equivalence mapping.

**Files to modify**: `scripts/run-stage-concepts.ts` — `main()` function, after combining both concept sets.

### D4: Implementation reference integrity validation

Add a post-generation validation step that checks all `implementation_refs` and `ancestry.derived_from` arrays against the canonical record set:

```typescript
function validateConceptRefs(
  concepts: ConceptRecord[],
  allRecords: CanonicalRecord[]
): { valid: ConceptRecord[]; deleted: string[]; dangling: { conceptKey: string; danglingRefs: string[] }[] } {
  const recordIds = new Set(allRecords.map(r => r.id));
  const dangling: { conceptKey: string; danglingRefs: string[] }[] = [];
  const deleted: string[] = [];

  const valid = concepts.flatMap(c => {
    const refs = c.implementation_refs ?? [];
    const validRefs = refs.filter((id: string) => recordIds.has(id));
    const bad = refs.filter((id: string) => !recordIds.has(id));
    if (bad.length > 0) {
      dangling.push({ conceptKey: c.key, danglingRefs: bad });
    }
    // If all refs are dangling, the concept has no implementation evidence — delete it
    if (validRefs.length === 0) {
      deleted.push(c.key);
      return [];
    }
    // Sync ancestry.derived_from with valid refs only
    const validDerivedFrom = (c.ancestry?.derived_from ?? []).filter((id: string) => recordIds.has(id));
    return [{ ...c, implementation_refs: validRefs, ancestry: { ...c.ancestry, derived_from: validDerivedFrom } }];
  });

  return { valid, deleted, dangling };
}
```

- If dangling refs are found, log a warning and strip them (keep the concept with valid refs only).
- If ALL `implementation_refs` are dangling, delete the concept entirely (a concept with zero implementation evidence is meaningless).
- Sync `ancestry.derived_from` to only include refs that resolve to existing records.
- Add a conformance test that verifies all concept `implementation_refs` resolve to existing records.

**Files to modify**: `scripts/run-stage-concepts.ts` — add `validateConceptRefs()`, call after concept generation. `tests/conformance/` — add test case `c14-concept-ref-integrity.test.ts`.

### D5: Obsidian wiki-link validation for concepts

The Obsidian builder already has link validation (`validateAllLinks` in `packages/builders/obsidian-builder/src/links.ts`, called from `build.ts`). Extend it to verify that concept `implementation_refs` rendered as wiki-links resolve to existing note paths.

**Files to modify**: `packages/builders/obsidian-builder/src/links.ts` — extend `validateAllLinks` to accept and check concept `implementation_refs` links. `packages/builders/obsidian-builder/src/build.ts` — pass concept ref links to the validator.

## Architectural fit

- **RFC-0001** (extraction methodology) — this RFC operates on the concept layer, which is downstream of extraction. RFC-0001's Principle 2 (factual extraction without loss) ensures that native attributes like Crawl's `resists` object are preserved as-is, enabling D1 to handle them at the concept layer.
- **PLAN-003** (knowledge base enrichment) — this RFC addresses quality issues in the concept generation path introduced by PLAN-003 task C-1 (auto-generate cross-game concepts).
- **`scripts/run-stage-concepts.ts`** — the primary file modified. This script is the concept generation pipeline, not a package. It imports from `@roguelike-games-ib/knowledge-core` and `@roguelike-games-ib/materializer` but does not modify them.
- **`packages/builders/obsidian-builder/src/links.ts`** — D5 extends the existing `validateAllLinks` function to check concept implementation_refs. The function is defined in `links.ts` and called from `build.ts`.
- **`apps/mcp`** — the MCP tool `get_concept_members` resolves `ancestry.derived_from` to records. D4's ref stripping and `derived_from` sync ensures MCP responses are clean.
- **`rgkb/concept@2` schema** — this RFC does not modify the concept record schema. All changes operate within the existing schema fields (`implementation_refs`, `ancestry.derived_from`).

## Rollout

- **Existing concepts** are regenerated from scratch on the next run of `scripts/run-stage-concepts.ts`. The script's `cleanConceptData()` function removes all previous concepts from the same `actor_id` before generating new ones. No migration is needed — old concepts are deleted and replaced.
- **Design concepts** (`design-*`) are generated by a separate script (`scripts/run-stage-design.ts`) with a different `actor_id`. They are unaffected by the allowlist change and will persist across the concept regeneration.
- **BrogueCE-only concepts** (`layered-terrain-promotion`, `runic-weapon`) are hand-crafted with a different `actor_id`. They are also unaffected.
- **New conformance test** (`c14-concept-ref-integrity.test.ts`) is additive — it does not modify existing tests.
- **Obsidian builder** changes (D5) are backward-compatible — `validateAllLinks` already validates relation and claim links; extending it to concept refs adds coverage without changing existing behavior.

## Alternatives considered

**A. Expand `NOISY_ATTRS` blocklist instead of switching to allowlist** — add `speed`, `hp`, `ac`, and other numeric attributes to the existing blocklist. Rejected because a blocklist is reactive — new attributes will produce noisy concepts unless explicitly blocked. An allowlist is proactive — new attributes must be explicitly approved before producing concepts. The allowlist is safer for long-term concept quality.

**B. Delete concepts with dangling refs instead of stripping** — if any ref is dangling, delete the entire concept. Rejected because a concept with 20 refs where 1 is dangling still has 19 valid implementation evidence points. Stripping the dangling ref and keeping the concept preserves the valid evidence. Only concepts where ALL refs are dangling are deleted.

**C. Handle object-valued attributes in the deriver instead of the concept script** — modify `scripts/run-stage-deriver.ts` to flatten object attributes into claims, then use claims for concept matching. Rejected because it couples the deriver to concept-generation concerns and increases derived data volume. The concept script can handle object attributes directly for semantic equivalence matching without affecting the deriver.

## Risks

- **Allowlist too restrictive**: Switching from blocklist to allowlist may exclude some currently valid concepts. Mitigation: review the current 22 exact-match concepts and ensure all their attributes are in the allowlist.
- **Object attribute handling complexity**: Crawl's `resists` object may have nested structures. Mitigation: test with actual Crawl data before committing.
- **Semantic dedup false positives**: An exact-match concept may be semantically related but not identical to a semantic equivalence concept. Mitigation: only dedup when the exact-match concept's attribute+value is a direct subset of the semantic mapping.
- **Agent misinterpretation**: agents may treat the `INFORMATIVE_ATTRS` allowlist as exhaustive and fail to add new attributes when new game data types are extracted. Mitigation: the allowlist is explicitly extensible — agents adding new extractors should review whether new attributes warrant concept generation and add them to the allowlist.
- **False-positive rate for ref validation**: if record IDs change due to re-extraction with different hashing, valid refs may appear dangling. Mitigation: record IDs are slug-based (`RefreshIdentityResolver`) and stable across re-extractions. Dangling refs indicate genuine data quality issues, not false positives.

- Agents MUST sync `ancestry.derived_from` with `implementation_refs` when stripping dangling refs — both arrays must only contain valid record IDs.

- Agents MUST NOT modify `packages/knowledge-core` — this RFC does not change the knowledge-core package.
- Agents MUST NOT weaken the `INFORMATIVE_ATTRS` allowlist by adding attributes without verifying they produce semantically meaningful concepts.
