# RFC-0011: Game design pattern library — concrete examples, pattern combinations, and anti-patterns

## Context

The design layer (RFC-0003) generated 469 concepts: 15 primitives, 31 pressures, 56 mutation vectors, 224 knobs, 93 counterplay patterns, 28 failure modes. These are abstract — they describe what a design dimension is, but not how specific games implement it.

### Current state

- **Design knobs** have `implementation_refs` pointing to definition records, but these are keyword-matched, not curated. A knob like "Elbereth engraving" might link to a NetHack item record, not to the specific mechanic.
- **No pattern combinations**: There is no way to say "procedural_generation + inventory_management + identification = the item knowledge pattern" — a common roguelike design pattern where procedural items create knowledge gaps that the player must close through risky identification.
- **No anti-pattern links**: Failure modes exist (28) but are not linked to the specific primitive combinations that trigger them.

## Problem

1. **Abstract without concrete**: A user reading "design-permadeath" knows it's a concept, but cannot see *how* NetHack implements it vs. how Crawl implements it — unless they manually browse 830 NetHack records.

2. **No pattern-level analysis**: The design layer models individual primitives and pressures, but not how they combine into recognizable game design patterns (e.g., "knowledge through risk", "escalating threat", "build diversity").

3. **Failure modes are disconnected**: "Degenerate identification" (failure mode) exists but is not linked to the combination of primitives that causes it (identification + consumable scarcity + permadeath).

## Architectural fit

- **RFC-0003** (design layer expansion) — this RFC extends the design layer created by RFC-0003. The 15 design primitives, 31 pressures, and 28 failure modes are the foundation for pattern combinations and anti-pattern links. The existing `scripts/run-stage-design.ts` script and its `cleanDesignData()` idempotency pattern will be extended.
- **RFC-0004** (cross-game analysis tools) — the MCP tools created by RFC-0004 (`find_cross_game_concepts`, `get_concept_coverage`) already enumerate concept types. The new `design_pattern` type will be automatically discovered by these tools. The new `find_design_patterns` and `get_pattern_examples` tools follow the same pattern: function in `derived.ts`, registration in `server.ts`, `readOnly: true`.
- **RFC-0009** (concept quality scoring) — new `design_pattern` concepts will receive quality scores during materialization. The scoring formula (coverage, evidence, richness) works for patterns without modification: coverage = fraction of games where present, evidence = implementation_refs count, richness = related concepts count. No scoring changes needed.
- **Concept schema** (`rgkb/concept@2`) — supports any `concept_type` string. The new `design_pattern` type is additive. The `concrete_examples` field is a new canonical field on concept records, stored alongside existing fields like `implementation_refs` and `ancestry`.
- **Relation types** — `TRIGGERED_BY_COMBINATION` is a new relation type added to `knowledge/ontology/relation-types.yaml`. It connects `failure_mode` concepts to `design_pattern` concepts, extending the design-space graph.
- **`run-stage-design.ts`** — the existing script manages all design-layer concepts using `ACTOR_ID = "design-primitives"` and `cleanDesignData()` for idempotent re-runs. Pattern records and concrete examples will be generated by extending this script, not creating new scripts. This follows the established pattern.
- **AGENTS.md** — no updates needed. The root `AGENTS.md` rules about extractor packages and CI gates are not affected. The `apps/web/AGENTS.md` conventions for `MODULE_CONTRACT` and `CHANGE_SUMMARY` comments apply to new web files.

## Decision

### D1: Concrete examples for design primitives

Add a `concrete_examples` field to design primitive concept records. This is a canonical field stored on the concept record itself, alongside existing fields like `implementation_refs` and `ancestry`:

```json
{
  "concrete_examples": [
    {
      "game": "nethack",
      "description": "Elbereth engraving creates a safe square that most monsters avoid. Players use it as an emergency safe zone during combat.",
      "record_refs": ["urn:roguelike-games-ib:record:..."],
      "source_file": "src/engrave.c"
    },
    {
      "game": "crawl",
      "description": "Sanctuary scrolls create a temporary no-monster zone. More reliable than Elbereth but consumable.",
      "record_refs": ["urn:roguelike-games-ib:record:..."],
      "source_file": "dat/des/scrolls/sanctuary.des"
    }
  ]
}
```

**Generation**: LLM-assisted curation. For each design primitive, prompt the LLM with the primitive definition + relevant game records, and ask for a concrete example. Human review before committing. LLM responses are cached in `systems-cache/llm-design-cache.json` for idempotent re-runs.

**Scope**: Start with the 15 design primitives (one example per game = ~60 examples). Expand to knobs in phase 2.

**Storage**: Examples are stored as a `concrete_examples` array on the existing concept record in `knowledge/concept/cross-game/concept/`. No separate directory needed — the field is part of the concept record JSONL.

### D2: Pattern combination records

New concept type `design_pattern` — a named combination of primitives that co-occur in games. This is distinct from existing concept types:
- `emergent_pattern` — patterns that emerge from gameplay interactions (not design intent)
- `synergy_pattern` — specific synergistic interactions between mechanics
- `design_pattern` — named combinations of design primitives that co-occur as intentional design choices

The `design_pattern` type models a higher level of abstraction: which primitives combine to form recognizable roguelike design archetypes (e.g., "Knowledge Through Risk", "Build Diversity").

```json
{
  "concept_type": "design_pattern",
  "title": "Knowledge Through Risk",
  "definition": "A design pattern where procedural generation creates unknown items, and the player must risk using them to learn their properties. The tension between curiosity and survival drives engagement.",
  "member_primitives": ["design-procedural_generation", "design-identification", "design-permadeath"],
  "member_pressures": ["pressure-information_scarcity", "pressure-consequence_persistence"],
  "games_where_present": ["nethack", "broguece", "crawl"],
  "games_where_absent": ["cataclysm-bn"]
}
```

**Initial patterns** (curated, ~10):
1. Knowledge Through Risk (procedural_generation + identification + permadeath)
2. Build Diversity (species + profession + skill_progression)
3. Escalating Threat (depth_scaling + resource_scarcity + permadeath)
4. Shop Economy (currency + item_durability + procedural_generation)
5. God Relationship (religion + piety + alignment)
6. Corpse Economy (corpse_mechanics + nutrition + mutation)
7. Stealth Alternative (stealth + evasion + information_gathering)
8. Save Scum Prevention (permadeath + save_system + meta_progression)
9. Branch Choice (dungeon_branches + risk_reward + progression_gating)
10. Asymmetric Combat (turn_based + action_point + tactical_positioning)

### D3: Anti-pattern links

Link failure modes to pattern combinations that trigger them. New relation type `TRIGGERED_BY_COMBINATION`:

```json
{
  "relation_type": "TRIGGERED_BY_COMBINATION",
  "source_record_id": "<failure_mode_id>",
  "target_record_id": "<design_pattern_id>",
  "qualifiers": {
    "trigger_conditions": "When identification is too expensive and permadeath is harsh, players avoid all unidentified items, reducing build diversity."
  }
}
```

**Why a new relation type**: The existing `CAN_FAIL_AS` relation connects a primitive to a failure mode (1:1). `TRIGGERED_BY_COMBINATION` connects a failure mode to a pattern combination (N:1) — it answers "which combination of primitives triggers this failure mode?" rather than "which primitive can fail?". The existing `COUNTERS` relation has the wrong directionality (counterplay → problem, not problem → combination).

**Files**: `knowledge/ontology/relation-types.yaml` — add `TRIGGERED_BY_COMBINATION`.

### D4: MCP tools

**`find_design_patterns`**: List all design patterns, optionally filtered by game or primitive.

**Input**: `{ game?: string; primitive_key?: string }`

**`get_pattern_examples`**: Return concrete examples for a design pattern, grouped by game.

**Input**: `{ pattern_key: string }`

**Files**: `apps/mcp/src/tools/derived.ts`, `apps/mcp/src/server.ts`

### D5: Web app pattern pages

- `/patterns` — index page listing all design patterns with game coverage badges
- Pattern detail page shows: member primitives, pressures, games where present/absent, concrete examples, related failure modes

**Files**: `apps/web/src/pages/patterns.astro`, `apps/web/src/lib/design-data.ts`

## Design

### TypeScript contracts

```typescript
// D1: concrete_examples field on concept records
interface ConcreteExample {
  game: string;
  description: string;
  record_refs: string[];
  source_file: string;
}

// D2: design_pattern concept record
interface DesignPatternConcept {
  concept_type: "design_pattern";
  title: string;
  definition: string;
  member_primitives: string[]; // concept keys
  member_pressures: string[]; // concept keys
  games_where_present: string[];
  games_where_absent: string[];
  ancestry: {
    derived_from: string[]; // member primitive concept IDs
    source_games: string[]; // games_where_present
  };
}

// D4: MCP tools
function findDesignPatterns(
  ctx: McpContext,
  input: { game?: string; primitive_key?: string },
): Envelope<DesignPatternListOutput>;

function getPatternExamples(
  ctx: McpContext,
  input: { pattern_key: string },
): Envelope<PatternExamplesOutput>;
```

### Edge cases

- **Pattern with no member primitives**: A pattern record must have at least 2 `member_primitives`. Patterns with fewer are invalid and skipped during generation.
- **Game in neither `games_where_present` nor `games_where_absent`**: Treated as "unknown" — the game is not listed in either field. The MCP tool returns `coverage: "unknown"` for such games.
- **Failure mode with no triggering combination**: No `TRIGGERED_BY_COMBINATION` relation is created. The failure mode still exists with its `CAN_FAIL_AS` relation from the primitive.
- **Concrete example with dangling `record_refs`**: The example is still valid — `record_refs` are best-effort links. The MCP tool returns the example with `record_refs` as-is; unresolved refs are noted but don't cause errors.
- **Pattern record quality scoring**: RFC-0009 scoring applies automatically. Coverage = `games_where_present.length / total_games`. Evidence = `member_primitives.length / EVIDENCE_TARGET`. Richness = related concepts count.

## Rollout

**Default behavior**: All new records and tools are immediately available upon implementation. No feature flags, no gradual rollout.

**Adoption path**: No migration needed — pattern records, concrete examples, and MCP tools are additive. Existing tools and pages continue to work unchanged. The next `pnpm materialize` run computes quality scores for new pattern records.

**Concrete examples**: LLM-assisted generation with human review. The script generates examples, the operator reviews and commits. Examples are marked with `epistemic.confidence: "inferred"` until verified.

**Pattern records**: Curated list of 10 patterns defined as constants in `run-stage-design.ts`. The script generates concept records and relations idempotently — `cleanDesignData()` removes records with `actor_id === "design-patterns"` before each run.

## Risks

- **LLM example quality**: LLM-generated examples may be inaccurate. Mitigation: human review before committing, mark examples with `epistemic.confidence: "inferred"`.
- **Pattern subjectivity**: Which patterns exist is subjective. Mitigation: start with 10 well-known roguelike patterns, document selection criteria.
- **Scope creep**: 224 design knobs × 4 games = 896 potential examples. Mitigation: phase 1 = primitives only (60 examples), phase 2 = knobs.
- **Agent misinterpretation**: agents may treat LLM-generated examples as authoritative. Mitigation: examples are marked `epistemic.confidence: "inferred"` and require human review before committing.
- **Performance**: LLM calls for 15 primitives × 4 games = 60 examples. At ~1s per call = ~1 minute. Acceptable for batch generation. Responses cached in `systems-cache/llm-design-cache.json`.

## Alternatives considered

**A1: Reuse `emergent_pattern` or `synergy_pattern` instead of new `design_pattern` type** — `emergent_pattern` models patterns that emerge from gameplay interactions, not intentional design choices. `synergy_pattern` models specific synergistic interactions between mechanics. Neither captures the semantics of named combinations of design primitives that co-occur as design archetypes. Rejected — `design_pattern` has distinct semantics.

**A2: Create separate scripts instead of extending `run-stage-design.ts`** — two new scripts (`run-stage-examples.ts`, `run-stage-patterns.ts`) would each need their own `cleanDesignData()` implementation, LLM integration, and concept envelope helpers. Rejected — extending the existing script follows the established pattern and reuses existing infrastructure.

**A3: Use existing `CAN_FAIL_AS` relation instead of new `TRIGGERED_BY_COMBINATION`** — `CAN_FAIL_AS` connects a primitive to a failure mode (1:1, at the primitive level). The anti-pattern link needs to connect a failure mode to a pattern combination (N:1, at the pattern level). Rejected — different semantics and cardinality.

**A4: Extend `find_cross_game_concepts` with `concept_type: design_pattern` filter instead of new MCP tool** — `find_cross_game_concepts` lists concepts by type but doesn't filter by `member_primitives` or `games_where_present`. The `find_design_patterns` tool provides pattern-specific filtering (by game, by primitive). Rejected — different filtering semantics.

**A5: Store concrete examples in a separate directory** — a new `knowledge/concept/cross-game/examples/` directory would break the established pattern of storing all concept records in `knowledge/concept/cross-game/concept/`. Rejected — examples are a field on the concept record, not separate records.

## Implementation notes for agents

- **Status gate**: This RFC must be in `accepted` status before implementation begins. Use `fo-idea-plan` to create the implementation plan and transition to `accepted`.
- **Use existing helpers**: Agents MUST use `makeConceptEnvelope()`, `makeRelationEnvelope()`, and `makeEvidenceEnvelope()` helpers from `run-stage-design.ts` for all new records.
- **Actor ID**: Use `ACTOR_ID = "design-patterns"` for pattern records and concrete examples. Extend `cleanDesignData()` to remove records with this actor ID before re-runs.
- **No new scripts**: Do NOT create `scripts/run-stage-examples.ts` or `scripts/run-stage-patterns.ts`. Extend `scripts/run-stage-design.ts` with new generation loops.
- **LLM integration**: Use `@ai-sdk/openai` with `OPENAI_API_KEY` from environment. Cache responses in `systems-cache/llm-design-cache.json` for idempotent re-runs. Include game record context in prompts.
- **Canonical field**: `concrete_examples` is a canonical field on concept records in `knowledge/concept/cross-game/concept/`. Do NOT create a separate directory.
- **MCP tools**: Register in `REQUIRED_TOOLS` with `readOnly: true`. Follow the pattern of existing tools in `derived.ts`.
- **Web app**: New `.astro` files must include `MODULE_CONTRACT` and `CHANGE_SUMMARY` comments per `apps/web/AGENTS.md`.
- **Content vs code**: An agent can write the script, tools, and pages. The concrete examples and pattern definitions are LLM-assisted with human review — mark with `epistemic.confidence: "inferred"`.
- **CI gates**: All CI checks must pass — `pnpm materialize`, `pnpm exec turbo run build:check`, `pnpm exec vitest --run`.
- **Validate**: Run `pnpm exec forge rfc.validate --id RFC-0011 --json` after changes to verify no mechanical violations.
