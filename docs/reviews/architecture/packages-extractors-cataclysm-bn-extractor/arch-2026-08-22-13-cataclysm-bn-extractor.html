Deepen the run() method into an Entity Pipeline

Problem

The run() method is a 280-line flat sequence of 4 entity-kind blocks. Each block walks files, reads text, parses JSON, iterates entries, resolves IDs, creates envelopes, builds records, writes records, creates evidence, writes evidence, and increments a counter. The blocks differ only in: directory list, parser function, record kind, slug strategy, attribute mapping, and whether namespaceDuplicateId is applied. Adding a new entity kind means appending another 60-line block and touching the population section.

Solution

Create a deep Entity Pipeline module that owns the parse→resolve→envelope→attributes→evidence→count flow. Each entity kind becomes a declarative specification (directory list, parser function, record kind, slug strategy, attribute mapper, dedup flag, evidence symbol). The pipeline iterates over specs, unifying all 4 blocks into one flow. Population counts are derived from specs, not hard-coded. The namespaceDuplicateId decision becomes a spec flag (dedup: true), not an inline call. This pattern is already proven in the broguece extractor's entity-pipeline.ts — see Candidate 03 for lifting it into the SDK.

Benefits

  • locality: all entity flow in one module
  • depth: run() becomes a spec list + pipeline call
  • leverage: new entity kinds are specs, not 60-line blocks
  • tests: each spec testable in isolation

Problem

computeLineRange(text, index, total) accepts an index parameter, but every call site passes 0 — meaning every entry in a JSON array gets the same line range (lines 1–6 of the file). The total parameter is never used. Evidence anchors point to the wrong lines for all entries except the first. The function is also shallow: its interface (text, index, total → line range) is nearly as complex as its implementation (14 lines), and the real complexity — finding where a specific JSON array element starts and ends in the source text — is not implemented at all.

Solution

Replace computeLineRange with a JSON offset tracker that maps each array element to its character range in the source text, then resolves those to line numbers. This can be done by scanning the raw text for object boundaries (brace counting) or by using a JSON parser that reports source positions. The tracker becomes a deep module: callers pass the text and receive per-entry line ranges through a small seam. All 4 parsers call it instead of the broken computeLineRange. Evidence anchors will point to the correct lines for every entry, not just the first.

Benefits

  • locality: offset-to-line logic in one module
  • depth: callers pass text, receive correct ranges
  • leverage: all 4 parsers get correct evidence anchors
  • tests: synthetic JSON with known line offsets

Problem

The broguece extractor invented the EntitySpec + runEntityPipeline pattern to solve the flat-run() problem. But that pattern lives in broguece-extractor/src/entity-pipeline.ts — it has no leverage beyond broguece. The cataclysm-bn and nethack extractors face the same problem but cannot reuse the solution. Each must either re-invent the pipeline or stay flat. The SDK defines the Extractor interface but provides no pipeline scaffolding, so the pattern is not shared.

Solution

Move EntitySpec and runEntityPipeline into the extractor SDK. Generalize the originActorId (currently hard-coded as "broguece-factual") to a spec or context parameter. The broguece, cataclysm-bn, and nethack extractors all import from the SDK. Each extractor's run() becomes a spec list + pipeline call. The SDK becomes the single source of truth for the entity flow pattern. This is a prerequisite for Candidate 01 — cataclysm-bn should not copy the pipeline a second time.

Benefits

  • locality: entity flow pattern in one SDK module
  • depth: SDK hides the parse→record→evidence loop
  • leverage: all 3 extractors benefit from pipeline fixes
  • tests: one pipeline test suite, not three

Problem

221 lines with 4 parsers, all following the same pattern: JSON.parse, check if array, loop elements, check id field, extract fields with ?? defaults, call extractName, call computeLineRange, return entries. The variation is only in which fields are extracted and the entry filter (monsters check type === "MONSTER", others just check id). The shared scaffolding is duplicated 4 times. The extractName helper is shared but the rest is copy-paste.

Solution

Create a generic parseJsonEntries<T> function that accepts a text, a predicate (entry filter), and a field extractor (maps a raw JSON object to a typed entry). Each parser becomes a spec: monster spec passes (o) => o.type === "MONSTER" and a 18-field extractor; item spec passes (o) => o.id and a 10-field extractor. The generic parser handles JSON.parse, array validation, iteration, name extraction, and line range computation. This pairs naturally with Candidate 02 — the line range tracker plugs into the generic parser as a shared concern.

Benefits

  • locality: JSON parsing scaffolding in one function
  • depth: each entity kind is a spec, not a parser
  • leverage: new entity kinds are specs, not 30-line functions
  • tests: spec-level tests with synthetic JSON fragments

Candidate 05

Derive population denominators from the manifest, not hard-coded

Speculative

Files

packages/extractors/cataclysm-bn-extractor/src/extractor.ts:39–64 (manifest) · lines 364–379 (writePopulation + populationCounts)

Problem

The manifest declares expected: 597 for monsters. The run() method calls ctx.output.writePopulation("monsters", 597, monsterCount) — the same number is hard-coded in two places. Same for items (5886), mutations (625), and professions (339). If the manifest's expected count changes, the run() method must be updated separately. This is not a deepening opportunity per se, but it is a friction point that disappears if population counts are derived from the manifest's exhaustivePopulations array.

Solution

At the end of run(), iterate over manifest.exhaustivePopulations to call writePopulation and build the populationCounts array. The mapping from spec to population dimension is already implicit in the spec list (Candidate 01). This is a one-loop change that eliminates 8 hard-coded numbers and keeps the manifest as the single source of truth for expected counts.

Benefits

  • locality: expected counts in manifest only
  • leverage: no drift between manifest and run()

Top recommendation

Deepen run() into an Entity Pipeline first

The 280-line run() method is the single largest source of friction. It forces every reader to hold 4 nearly-identical entity-kind blocks in their head simultaneously, with the namespaceDuplicateId decision scattered across two of them. The broguece extractor already proved this pattern works — EntitySpec + runEntityPipeline turned a 390-line flat sequence into a declarative spec list. But that pattern is trapped in the broguece package (Candidate 03). Deepening cataclysm-bn's run() creates the immediate pressure to lift the pipeline into the SDK, which in turn benefits nethack. Candidate 02 (fixing computeLineRange) should follow immediately after — the broken line ranges produce incorrect evidence anchors for every entry except the first in each file.

1. Declarative entity specs
2. Unified record writing
3. Fix evidence line ranges
4. Lift pipeline to SDK
