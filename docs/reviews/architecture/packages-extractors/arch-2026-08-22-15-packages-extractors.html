Problem

The broguece-extractor package contains entity-pipeline.ts (106 lines) with its own EntitySpec interface and runEntityPipeline function. But extractor.ts line 53 imports runEntityPipeline and EntitySpec from @roguelike-games-ib/extractor-sdk, not from the local file. The local entity-pipeline.ts is dead code — a leftover from when the pipeline was lifted into the SDK (see cataclysm-bn review Candidate 03, now implemented). The two EntitySpec interfaces have diverged: the SDK version uses getSourcePath() and getSymbolName() as functions; the dead local version uses sourcePath and symbolName as string fields, couples with SpritePipeline, and hard-codes originActorId: "broguece-factual". A reader encountering both files must waste time determining which is live.

Solution

Delete packages/extractors/broguece-extractor/src/entity-pipeline.ts. The SDK's entity-pipeline.ts is the single source of truth. The broguece index.ts already re-exports from the SDK, so no downstream imports break. Apply the deletion test: deleting the dead file concentrates understanding — one pipeline, one EntitySpec shape, no divergence to reason about.

Benefits

  • locality: one pipeline module, not two
  • depth: no shallow duplicate to confuse readers
  • leverage: SDK pipeline is the only shape to learn
  • tests: no dead test surface to maintain

Problem

runEntityPipeline returns counts: number[] — a positional array indexed by spec order. Each extractor then maps these positions to population dimensions with fragile arithmetic. BrogueCE uses counts[0], counts[1], counts[2 + i] for variable-length item specs, and counts[simpleStartIdx + N] for 7 simple specs — with a comment listing the indices. Cataclysm-BN uses counts[0] through counts[3]. NetHack uses a ternary on the dimension string. If the spec list order changes, the mapping breaks silently — no type error, just wrong population counts. The pipeline knows the spec order but throws that information away by returning a bare array.

Solution

Add an optional populationDimension?: string field to EntitySpec. When present, the pipeline includes the count in a Map<string, number> returned alongside the existing counts array (for backward compatibility). Each extractor's spec already knows its dimension — it just doesn't declare it on the spec. The population mapping at the end of run() becomes a simple lookup against manifest.exhaustivePopulations using the map, eliminating all positional arithmetic. BrogueCE's 13-line index calculation, cataclysm-bn's 4-line positional mapping, and nethack's ternary all collapse into one for...of loop over the manifest.

Benefits

  • locality: dimension lives on the spec, not in a separate mapping
  • depth: pipeline returns semantically keyed counts, not a bare array
  • leverage: all 3 extractors drop positional arithmetic
  • tests: spec-level population assertion, no index math

Problem

The BrogueCE extractor handles image assets with a 55-line inline flow in run() (lines 390–445) that walks the source tree, creates record envelopes, builds evidence, and counts — all duplicated from the Entity Pipeline pattern. The flow uses a different source strategy (tree walk vs. catalog parse) but the record/evidence writing is identical. readImageMedia (20 lines) and MIME_MAP/IMAGE_EXTENSIONS are defined at module scope but only used here. The image flow has no locality — understanding it requires reading the inline code, the module constants, and the readImageMedia function separately.

Solution

Create an image asset adapter that walks the source tree and produces ImageAssetEntry[] — each entry carries path, MIME type, dimensions, and file name. Feed these entries into the Entity Pipeline as a regular EntitySpec with kind: "image_asset". The adapter owns the MIME_MAP, IMAGE_EXTENSIONS, and readImageMedia logic behind a single seam. The pipeline handles record/evidence writing, eliminating the duplicated flow. The run() method becomes a spec list + pipeline call with no special-case branching for image assets.

Benefits

  • locality: image walk + media reading in one adapter
  • depth: run() has no special-case flow for images
  • leverage: pipeline handles record/evidence for all kinds
  • tests: image adapter testable in isolation

Problem

The cataclysm-bn extractor maps data through three layers: JSON parsers produce typed entries (MonsterEntry, ItemEntry, etc.), then collectEntries/collectProfessionEntries convert them to CataclysmEntry (a generic intermediate with attributes: Record<string, unknown>), then cataclysmSpec maps CataclysmEntry fields 1:1 to EntitySpec callbacks. The cataclysmSpec function is 16 lines of pure pass-through — getSlug: (e) => e.slug, getNativeId: (e) => e.nativeId, etc. The CataclysmEntry type erases all type information from the parsed entries (attributes becomes a generic record). Deletion test: deleting CataclysmEntry and cataclysmSpec would concentrate the mapping into the parser functions, which already know the field names.

Solution

Have each parser function produce an EntitySpec directly, using the existing typed entry interfaces (MonsterEntry, ItemEntry, etc.) as the generic parameter. The collectEntries function returns EntitySpec[] instead of CataclysmEntry[]. The CataclysmEntry interface, cataclysmSpec function, and the collectProfessionEntries special-case all collapse. Each parser's spec builder encodes its kind, slug strategy, nativeId, and attribute mapping — the same information that monsterParser/itemParser currently produce as CataclysmEntry fields. The namespaceDuplicateId call stays in the parser, where it already lives.

Benefits

  • locality: parser owns the full entry→spec mapping
  • depth: no shallow pass-through layer
  • leverage: type safety preserved from JSON to EntitySpec
  • tests: parser tests produce specs, not intermediates

Problem

simpleSpec is a 31-line factory that accepts 7 callbacks in an opts object and wraps them in a closure that returns an EntitySpec. The only transformation it performs is injecting originActorId: "broguece-factual" and wrapping getAttributes in async. The interface (7 callbacks in, 7 callbacks out) is nearly as complex as the implementation. Deletion test: deleting simpleSpec and inlining the 7 call sites would add originActorId and async at each site — not enough complexity to concentrate. The function is a shallow adapter that doesn't hide meaningful complexity.

Solution

Two options. Option A (inline): Delete simpleSpec and build EntitySpec objects directly at each call site. The 7 call sites already provide all callbacks — adding originActorId and async is 2 lines per site. This removes a shallow layer without losing anything. Option B (deepen): If Candidate 02 is implemented, simpleSpec becomes deeper by also owning the populationDimension and potentially the evidence kind. Then it hides meaningful complexity — the caller provides callbacks + dimension, and simpleSpec assembles the full spec. Option B is preferred if Candidate 02 proceeds; Option A is the fallback.

Benefits

  • locality: spec construction at the call site (A) or deeper factory (B)
  • depth: no shallow pass-through (A) or meaningful assembly (B)
  • leverage: 7 call sites simplified either way
  • tests: specs testable directly

Top recommendation

Delete the dead broguece entity-pipeline.ts first

The dead entity-pipeline.ts in broguece-extractor is the lowest-risk, highest-clarity change. It's 106 lines of code that no one imports — a leftover from when the pipeline was lifted into the SDK. Every reader who opens the broguece package sees two pipeline files and must determine which is live. Deleting it costs nothing and immediately concentrates understanding. After that, Candidate 02 (population dimension in EntitySpec) delivers the most cross-extractor leverage: it eliminates fragile positional arithmetic in all three extractors and makes the spec-to-population mapping type-safe. Candidates 03 and 04 are package-local improvements that can follow.
