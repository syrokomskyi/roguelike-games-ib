Problem

The run() method is a 390-line flat sequence of 11 entity-type blocks. Three blocks (creatures, terrain, items) use inline envelope+record+evidence construction; seven use the writeEntityRecord helper with a 14-field interface. Adding a new entity kind means appending another block and touching the population section. Two record-writing patterns coexist without reason — the helper was added later but the first three were never migrated.

Solution

Create a deep Entity Pipeline module that owns the parse→resolve→envelope→attributes→evidence→count flow. Each entity kind becomes a declarative specification (parse function, record kind, native kind, slug strategy, attribute mapper, evidence symbol). The pipeline iterates over specs, unifying both record-writing patterns. Population counts are derived from specs, not hard-coded. Sprite extraction becomes an adapter passed to the pipeline.

Benefits

  • locality: all entity flow in one module
  • depth: run() becomes a one-liner
  • leverage: new entity kinds are specs, not blocks
  • tests: each spec testable in isolation

Problem

853 lines with 10 parsers, 7 of which follow the same pattern: split lines, find catalog start, loop until };, match comment or string for entry name, accumulate multi-line entries, extract fields via regex. The shared scaffolding is duplicated. parseEntryFields (lines 330–356) handles nested braces and strings correctly but is only used by the item table parser — the other 6 catalog parsers use naive split(",") which breaks on nested braces.

Solution

Create a deep C Catalog Parser module that encapsulates the line-scanning, entry-detection, multi-line-accumulation, and field-extraction patterns. Each catalog becomes a specification (start marker pattern, entry detector, field extractors) rather than a full function. parseEntryFields becomes the shared field extractor for all parsers, fixing the latent nested-brace bug in the 6 catalog parsers that use naive splitting.

Benefits

  • locality: parsing scaffolding in one place
  • depth: each catalog is a spec, not a function
  • leverage: new catalogs are specs, not 50-line functions
  • tests: spec-level tests with synthetic C fragments

Problem

The envelope construction (schema, id, key, record_type, language, scope, origin, epistemic, aliases) is duplicated identically across all three extractors. The broguece version passes recordType as a parameter; the other two don't — a silent drift. The SDK defines the types but not the builder, so each extractor re-implements the same 20-line function.

Solution

Add a createRecordEnvelope function to the extractor SDK, behind the existing seam. Extractors call it instead of re-implementing it. The SDK becomes the single source of truth for envelope shape. The recordType parameter drift is resolved by making it optional with a default of "definition".

Benefits

  • locality: envelope shape in one module
  • depth: SDK hides envelope construction
  • leverage: all extractors benefit from fixes
  • tests: one envelope test, not three

Problem

Glyph mapping, tile coordinate math, and sprite file I/O are interleaved with record writing in run(). Four module-level functions (53 lines) exist only to serve run(). The process.cwd() call (line 306) makes the extractor environment-sensitive — the sprite output directory depends on the working directory, not the context. readPngDimensions is used for image_asset records but lives next to sprite code, creating false locality.

Solution

Create a Sprite Pipeline module that owns glyph-to-coordinate mapping, tile sheet reading, sprite extraction, and PNG dimension reading. The extractor passes glyph + tile sheet buffer; the pipeline returns a relative path. The output directory is passed via the extractor context, not process.cwd(). The pipeline is an adapter that the Entity Pipeline (Candidate 01) can call per-entity.

Benefits

  • locality: all sprite logic in one module
  • depth: glyph math hidden behind a seam
  • leverage: testable without real source tree
  • tests: synthetic tile sheet fixtures

Candidate 05

Fix the stale index.ts barrel export

Speculative

Files

packages/extractors/broguece-extractor/src/index.ts

Problem

The barrel exports parseEnum, parseMonsterCatalog, parseTileCatalog, parseItemTable but not the 7 newer parsers (parseDungeonFeatureCatalog, etc.). Meanwhile extractor.ts imports those 7 directly from c-parser.ts, bypassing the barrel. External consumers who import from the barrel cannot access the newer parsers.

Solution

Update the barrel to export all 10 parsers and their types. This is a one-line fix, not a deepening — but it signals that the barrel is not maintained as new parsers are added. If Candidate 02 (Catalog Parser factory) is implemented, the barrel would export the factory + spec types instead.

Benefits

  • locality: barrel is the single import surface
  • leverage: external consumers get all parsers

Top recommendation

Deepen run() into an Entity Pipeline first

The 390-line run() method is the single largest source of friction. It forces every reader to hold 11 entity-type blocks in their head simultaneously, hosts two contradictory record-writing patterns, and interleaves sprite extraction with record construction. Deepening it into an Entity Pipeline creates the seam that Candidates 02 and 04 plug into — the catalog parser becomes a spec, and the sprite pipeline becomes an adapter. Without this deepening first, the other candidates improve parts without improving the whole.

1. Declarative entity specs
2. Unified record writing
3. Population from specs
4. Sprite as adapter
