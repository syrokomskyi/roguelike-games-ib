Problem

createExtractorContext is a 7-parameter passthrough — its interface is as complex as its implementation (one object literal). Every caller manually constructs 6 dependencies with compatible parameters (sourceId, sourceRoot, binding, etc.). The quality harness creates a fresh context per test (8 checks × 8 lines each). runExtractorDeterministic lives in the same module but is a separate concern — it runs the extractor twice and hashes, which is a verification concern, not a context-assembly concern.

Solution

Create a deep ExtractorRunner module that owns the full run lifecycle: constructing all 6 dependencies from high-level parameters, calling extractor.run(ctx), resolving populations, flushing output, and optionally verifying determinism. The interface shrinks to runner.run(extractor, options) where options is { sourceRoot, binding, keyRegistry, aliasRegistry, schemas, stagingDir }. The current createExtractorContext becomes an internal detail. runExtractorDeterministic becomes runner.verifyDeterministic(extractor, options).

Benefits

  • locality: all run-lifecycle steps in one module
  • depth: callers pass 3 params, not 6 constructor calls
  • leverage: every test and production invocation benefits
  • tests: one mock interface, not 6 constructor mocks

Problem

resolvePopulationCounts and checkRecordLoss are pure functions extracted for testability, but no extractor calls them. All three extractors inline the same 5-line pattern: map manifest.exhaustivePopulations → write each to ctx.output → reduce for recordCount. The functions have no locality — the real bugs hide in the callers' copy-pasted code, not in the tested pure functions. BogueCE additionally mixes in a non-manifest population (image_assets), making the pattern diverge.

Solution

Create a PopulationCollector that owns the full resolve→write→count flow. It takes (manifest, dimensionCounts, ctx.output) and internally resolves counts, writes populations, computes recordCount, and optionally checks record loss. Extractors call one method instead of inlining the pattern. The existing pure functions become internal implementation details. The BrogueCE image_assets extra population is handled by allowing the caller to pass additional ad-hoc populations alongside the manifest.

Benefits

  • locality: population flow in one module, not 3 copies
  • depth: one method replaces 5 inlined lines per extractor
  • leverage: new extractors get population handling for free
  • tests: test the collector, not 3 duplicate caller patterns

Problem

EvidenceFactory takes a raw sourceRoot: string and does its own resolve() + readFileSync(). This bypasses the ReadonlySourceReader sandbox — no path-traversal check, no symlink-escape check. Two modules independently resolve and read files from the same root. The caller must ensure sourceRoot matches between the reader and the factory, but nothing enforces this.

Solution

Change EvidenceFactory to receive a ReadonlySourceReader instead of a sourceRoot string. The factory calls reader.readBytes() for SHA-256 and reader.readText() for fragment hashes. Path resolution goes through reader.resolveSafe(). The sandbox is the single I/O seam. The constructor becomes EvidenceFactory(sourceId, bindingDigest, reader).

Benefits

  • locality: all file I/O behind one sandboxed seam
  • depth: sandbox guarantees extend to evidence hashing
  • leverage: no caller-side sourceRoot matching needed
  • tests: mock ReadonlySourceReader, not fs + path

Problem

EntitySpec<E> has 13 fields, most of which are getter functions. Every extractor must implement all 13 — even when 8 are constant per extractor (e.g. originActorId, getSourcePath pattern). The broguece extractor created a simpleSpec helper with 9 parameters as a workaround, proving the interface is too wide. The deletion test fails: deleting EntitySpec would just move the 13 fields into each extractor's inline code — but the friction is in the shape, not the count. The pipeline pushes complexity to the caller instead of absorbing it.

Solution

Split EntitySpec into a 3-field base (kind, entries, adapter) and an EntityAdapter<E> interface that groups the 12 getters into cohesive clusters: identity (constant per extractor), resolve(entry) (slug + nativeId + sourcePath + symbolName + dataKey), names(entry), attributes(entry), evidence(entry), skip?(entry). Provide a createEntityAdapter builder with defaults for constant fields. The pipeline's runEntityPipeline calls spec.adapter.resolve(entry) instead of 6 individual getters. The simpleSpec workaround becomes unnecessary.

Benefits

  • locality: adapter groups related getters cohesively
  • depth: pipeline absorbs resolution logic, not just dispatches
  • leverage: new entity kinds need only an adapter, not 13 fields
  • tests: adapter is mockable as one unit

Top recommendation

Deepen context assembly into an ExtractorRunner first

The createExtractorContext passthrough is the single largest source of friction for every consumer of the SDK. Every test, every quality check, and every production invocation manually constructs 6 dependencies with compatible parameters. Deepening this into an ExtractorRunner creates the seam that Candidate 02 (PopulationCollector) plugs into — the runner owns the lifecycle, the collector owns the population flow within it. Candidate 03 (EvidenceFactory seam leak) becomes a natural part of the runner's internal construction: the runner creates the ReadonlySourceReader once and passes it to both the context and the EvidenceFactory. Without this deepening first, the other candidates improve parts without improving the whole.
