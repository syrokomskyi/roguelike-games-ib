Deepen the C-macro scanner — extract the duplicated paren-depth accumulation loop

Problem

All three parsers (parseMonsters, parseObjects, parseArtifacts) share the same core loop: scan lines, match a macro pattern, accumulate multi-line text by tracking paren depth, then hand off to a finalize*Entry function. The accumulation loop (10 lines) is copied verbatim into each parser. The preprocessor directive handling (25 lines of #if/#ifdef/#endif logic) is inline in parseObjects only — if monsters.h ever gains #if 0 blocks, parseMonsters will silently parse dead code. Understanding the shared scanning pattern requires reading all three parsers and noticing the duplication.

Solution

Create a deep scanCMacros module that owns the line-scanning, macro-matching, paren-depth-accumulation, and optional preprocessor filtering. Its seam: caller provides source text, a macro regex, and an optional preprocessor-handling flag. The module returns {fullText, lineStart, lineEnd}[] — one entry per matched macro invocation. Each parser becomes a thin wrapper: call scanCMacros, map results through the finalize function. The preprocessor filter becomes a pluggable option, not 25 inline lines. Adding a new entity kind (e.g., artifacts) is a new finalize function + a scanCMacros call, not a 50-line parser.

Benefits

  • locality: macro scanning logic in one module
  • depth: callers pass pattern, receive raw invocations
  • leverage: preprocessor handling available to all parsers
  • tests: synthetic C fragments with known paren nesting

Problem

finalizeMonsterEntry (73 lines) and finalizeObjectEntry (78 lines) are long sequences of regex matches with fallback defaults. Each field is extracted by its own regex, and failures are silent — a mismatched regex returns 0, "S_UNKNOWN", or "CLR_GRAY" with no diagnostic. The object parser's positional regexes (e.g., ,\s*(\d+)\s*,\s*\d+\s*,\s*\d+\s*,\s*\d+\s*,\s*\d+ for cost) are particularly fragile: if the C macro format adds or removes a parameter, the regex silently matches the wrong field. There is no locality — debugging a single field requires reading the entire function and tracing which regex might be failing.

Solution

Replace the regex chains with a declarative field map: an array of {name, regex, group, transform, default} objects. A single extraction engine iterates over the field map, applies each regex, transforms the captured group, and falls back to the default on mismatch. Required fields (e.g., name, SIZ presence) are validated explicitly. The monster field map (20 specs) and object field map (9 specs) become data, not code. Each field is testable in isolation: pass a synthetic C fragment, assert the extracted value. The engine can optionally emit diagnostics for fields that fell back to defaults, making silent parse failures visible.

Benefits

  • locality: each field defined in one place, not scattered
  • depth: extraction engine hides regex application loop
  • leverage: new fields are specs, not regex lines
  • tests: per-field unit tests with synthetic fragments

Problem

parseArtifacts (57 lines) is exported from index.ts but never imported by extractor.ts. It matches OBJECT(\s*OBJ( patterns — a subset of what parseObjects already handles (the OBJECT macro is in the OBJECT_MACROS table). Artifact entries are already extracted as items by parseObjects. The function is dead code that adds maintenance burden and confuses readers who expect it to be called.

Solution

Option A (remove): Delete parseArtifacts and its export from index.ts. Artifacts are already covered by parseObjects. Option B (integrate): If artifacts should be a separate entity kind (e.g., artifact vs item), add an EntitySpec for artifacts in extractor.ts and filter them out of parseObjects to avoid double-counting. This requires deciding whether artifacts are a distinct knowledge kind or just items with special flags.

Benefits

  • locality: no dead code confusing readers
  • depth: clearer module surface for c-parser.ts
  • leverage: Option B adds a new entity kind via a spec
  • tests: either way, artifact coverage is explicit

Problem

25 lines of C preprocessor directive handling (#if, #ifdef, #ifndef, #endif, #else, #elif) are inline in parseObjects. This logic is a cross-cutting concern for any C header parser, but only parseObjects has it. parseMonsters and parseArtifacts have no preprocessor handling — if monsters.h contains #if 0 blocks (which it does in some NetHack variants), those entries will be parsed as live code. The preprocessor logic is also shallow: its interface (line iterator + skipDepth state) is nearly as complex as its implementation.

Solution

Extract a createPreprocessorFilter function that wraps a line iterator and yields only lines outside of skipped preprocessor blocks. The filter owns the skipDepth state and the conditional logic. It can be composed with the C-macro scanner from Candidate 01: the scanner accepts an optional filter, and all parsers gain preprocessor safety without duplicating the logic. The filter's seam is small: {isSkipped(line): boolean} or a generator that yields only active lines.

Benefits

  • locality: preprocessor logic in one module
  • depth: callers pass lines, receive filtered lines
  • leverage: all parsers gain #if 0 safety
  • tests: synthetic C with known preprocessor blocks

Top recommendation

Deepen the C-macro scanner first

The duplicated paren-depth accumulation loop is the single largest source of friction in c-parser.ts. It forces every reader to hold three nearly-identical scanning loops in their head simultaneously, and the preprocessor handling is trapped in only one of them. Extracting a deep scanCMacros module concentrates the scanning logic behind a small seam, makes preprocessor filtering available to all parsers (Candidate 04 plugs in naturally), and reduces each parser to a finalize function + a scanner call. Candidate 02 (declarative field extraction) should follow — it's easier to design field maps when the parsers are already thin wrappers. Candidate 03 (parseArtifacts dead code) is a quick cleanup that can happen anytime.
