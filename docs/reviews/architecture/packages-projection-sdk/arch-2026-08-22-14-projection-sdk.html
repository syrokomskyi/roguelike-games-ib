Deepen ProjectionStore — absorb shallow query modules

Problem

ProjectionStore is a struct with 11 public fields. Six submodules each wrap a read function (only called from openProjection) and 1–2 one-liner query helpers. The modules are shallow — interface ≈ implementation. Every consumer reaches into raw arrays and calls free functions, so there is no locality: the logic for "evidence for a record" is duplicated in render-record.ts and web/evidence.ts independently.

Solution

Make ProjectionStore a deep module. The read functions become private implementation details of openProjection. The one-liner query helpers become methods on the store. Consumers interact through the store's interface — resolveRecord, claimsForRecord, relationsForRecord, evidenceForRecord — not by reaching into raw arrays and calling free functions. The store owns its data and provides query operations with locality.

Benefits

  • locality: all projection query logic in one module
  • leverage: one interface for all query operations
  • depth: store interface smaller than implementation
  • tests: test through store interface, not raw arrays

Problem

records.ts exports five functions — findRecordById, findRecordByKey, resolveKeyToId, resolveAliasToKey, resolveAliasToId — that no consumer ever calls. The open.ts versions (resolveRecordById, resolveRecordByKey, resolveRecordByAlias, resolveRecord) are used instead. Two parallel APIs for the same concept; one is dead weight that confuses AI navigation.

Solution

Delete the five unused functions from records.ts and remove their exports from index.ts. Keep only readRecords, readKeyMap, readAliasMap (used internally by openProjection) and the KeyMap and AliasMap types. If Candidate 01 is adopted, these survivors become private to the deepened ProjectionStore.

Benefits

  • locality: one resolution path
  • leverage: less surface to learn
  • depth: fewer trivial wrappers
  • tests: no dead code to maintain

Problem

authority.ts exports six symbols. canonicalAuthority is called once (from openProjection). laboratoryAuthority, isCanonical, and isLaboratory have zero callers. The AuthorityContext field on ProjectionStore is set but never read by any consumer. The laboratory-runtime package has its own independent isCanonicalRecordId / isLaboratoryRecordId — it does not use projection-sdk's authority at all. The module is speculative.

Solution

Remove authority.ts entirely. Drop the authority field from ProjectionStore. The canonicalHash already identifies the projection's authority — a separate AuthorityContext wrapper adds no value until a second authority type actually needs to flow through the store. If that day comes, add the module then with real consumers.

Benefits

  • locality: no dead concepts to navigate
  • leverage: simpler store interface
  • depth: no speculative abstraction
  • tests: no dead paths to cover

Deduplicate manifest validation

                flowchart TD

                  OP -->|read + validate once| M1
                  OP -->|exposes manifest| PS[ProjectionStore]
                  CW -->|reads from store| PS
                  class OP,PS deep

Problem

openProjection reads and validates the manifest. createWebContext independently reads and validates the same manifest, then calls openProjection which reads and validates again. createMcpContext reads the manifest separately too. verifyMaterialization does its own read-and-validate. The same file is read and checked 2–3 times for the same distDir.

Solution

openProjection is the single validation point. It already throws on unsupported schema. Expose the manifest (or its metadata fields) through ProjectionStore so callers don't need to re-read. createWebContext and createMcpContext call openProjection and get the manifest from the store. verifyMaterialization keeps its own lightweight check since it runs before opening a store.

Benefits

  • locality: one validation path
  • leverage: manifest from store, not re-read
  • depth: openProjection owns validation
  • tests: one test for manifest validation

Top recommendation

Deepen ProjectionStore first

It is the root deepening that subsumes the others. When ProjectionStore becomes a deep module, the six shallow satellite modules collapse into private implementation details, the dead resolution API in records.ts disappears, and the manifest validation can be internalized. The store gains locality — all query logic lives behind one interface — and consumers stop reaching into raw arrays. This also creates the first testable seam: today there are zero test files for projection-sdk because there is no interface to test through.
